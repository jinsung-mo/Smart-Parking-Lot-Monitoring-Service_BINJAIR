# BINJARI | 빈자리

**카메라 영상으로 빈 주차면을 찾아 지도와 앱에 표시하는 서비스입니다.** 주차면마다 별도 센서를 설치하는 대신, 영상에서 빈자리와 점유 영역을 찾고 각 주차면의 상태를 판단합니다.

창원대학교 컴퓨터공학과 캡스톤 디자인 프로젝트로, 55호관과 도서관 주차장 **2곳의 주차면 56개**를 대상으로 구현했습니다. 교내 소프트웨어 전시회에서 **인기상**을 받았습니다.

<img src="assets/icons/app_icon.png" width="88" alt="BINJARI 앱 아이콘">

## 왜 만들었나요?

주차장 위치를 알아도 어느 곳에 빈자리가 있는지는 도착해서 둘러봐야 합니다. BINJARI는 출발 전에 주차장별 빈자리 수를 확인하고, 도착한 뒤에는 어느 주차면이 비어 있는지 찾도록 돕기 위해 만들었습니다. 현재 상태만으로 방문 시간을 고르기 어려운 경우에는 시간대별 점유율도 함께 보여줍니다.

## 실제 주차장 영상 분석

직접 촬영한 55호관 영상에 **학습된 YOLOv8x**와 현재 Flask 판정 코드를 실행했습니다. 왼쪽에는 모델이 찾은 빈자리와 점유 영역을 박스로 표시했습니다. 오른쪽은 그 결과를 미리 정한 주차면 다각형에 연결하고 시간 필터를 거친 상태입니다. 빨간색은 점유, 초록색은 빈자리입니다. 녹화 영상의 일부 구간을 다시 분석한 결과입니다.

## 주요 기능과 실행 화면

## 시스템 아키텍처

![BINJARI 시스템 아키텍처: 영상 입력부터 Flutter 앱까지의 데이터 흐름](docs/images/system-architecture.svg)

분석 서버가 영상을 읽고 YOLOv8x로 빈자리와 점유 영역을 찾습니다. 모델을 실행해 이 결과를 얻는 과정을 추론이라고 합니다. 서버는 탐지 결과를 각 주차면에 연결해 상태를 판정하고 기록을 저장합니다. Flutter 앱은 서버 API에서 현재 상태와 통계를 받아 보여줍니다.

영상 파일로도 실행할 수 있습니다. 분석할 영상과 주차면 좌표는 관리자 기능에서 설정합니다.

### 다른 기술과 비교하면 어떤 점이 맞았나요?

BINJARI는 두 사람이 주차장 두 곳을 대상으로 만든 서비스입니다. 이 규모에서는 **영상 분석과 앱을 연결하는 데 드는 작업, 서버 운영 부담, 기존 코드의 재사용**을 기준으로 기술의 적합성을 설명할 수 있습니다. 아래 비교는 현재 구현과 요구사항을 바탕으로 정리한 근거입니다. 당시 모든 대안을 시험했다거나 성능을 비교 측정했다는 뜻은 아닙니다.

| 사용 기술 | 비교할 만한 대안 | 이 프로젝트에 맞는 이유 |
| --- | --- | --- |
| Flutter | Android/iOS 개별 개발, React Native | 지도와 주차 상태, 통계 화면을 공통 코드로 관리하고 같은 API에 연결 |
| Flask | Django, FastAPI | Flutter에 관리 화면을 두고 필요한 API만 Python 분석 코드에 연결하는 간단한 서버 구성 |
| YOLOv8x | YOLOv5, YOLOv8n/s | 빈자리와 점유 영역을 학습한 기존 가중치를 현재 분석 코드에 연결해 사용 |
| OpenCV | Pillow, imageio와 별도 배열 연산 | 영상 읽기부터 주차면 마스크의 교차 면적 계산, 결과 표시까지 한 흐름에서 처리 |
| SQLite | MySQL, PostgreSQL | 한 분석 서버 안에서 상태와 이력을 저장하고 시간대별 통계를 SQL로 조회 |
| Google Maps | 네이버 지도, 카카오맵, OpenStreetMap 기반 지도 | Flutter 플러그인으로 주차장 위치와 선택 동작을 연결하고 모바일과 웹의 지도 코드를 공유 |

<details>
<summary><strong>Flutter — 모바일 화면을 따로 두 벌 만들지 않기</strong></summary>

주요 화면은 지도, 주차면 상태, 시간대별 그래프입니다. Android와 iOS를 각각 개발하면 같은 API 응답을 처리하는 모델과 화면 변경도 플랫폼별로 관리해야 합니다. Flutter에서는 이 부분을 Dart 코드로 공유하고, 사용자 화면과 관리자 화면도 같은 앱에서 관리합니다. 여러 플랫폼에서 코드를 재사용하는 구조는 [Flutter 공식 문서](https://docs.flutter.dev/resources/architectural-overview)에서도 설명합니다.

BINJARI는 주차면 상태도와 점유율 그래프를 `CustomPainter`로 직접 그립니다. 주차면 색상, 번호, 막대그래프를 Flutter의 화면 상태와 같은 Dart 코드 안에서 다룰 수 있어, 별도 웹 화면을 삽입하지 않고 맞춤 화면을 구성하는 데 적합합니다. [주차면 그리기](lib/widgets/parking_lot_view.dart), [그래프 그리기](lib/screens/statistics_screen.dart)

React Native도 공통 코드와 맞춤 화면을 지원하는 대안이므로, 이 기능만으로 Flutter가 더 우수하다고 단정할 수는 없습니다. Flutter의 이점은 이 프로젝트에 필요한 화면을 한 코드베이스에서 다룰 수 있다는 데 있습니다. 다만 지도 키, 권한, 플러그인 설정은 플랫폼별로 필요하며, 공통 코드가 있다고 모든 플랫폼에서 동일하게 동작하는 것은 아닙니다. [실제 의존성](pubspec.yaml)

</details>

<details>
<summary><strong>Flask — 영상 처리 코드를 그대로 주차 상태 API에 연결하기</strong></summary>

서버에서 하는 주요 작업은 영상을 읽고, 모델 결과를 주차면 상태로 바꾸고, 현재 상태와 통계를 반환하는 것입니다. 추론과 OpenCV 처리가 이미 Python이므로 Flask에서도 같은 함수와 데이터를 사용합니다. 다른 언어의 API 서버를 추가하고 분석 결과를 전달하는 별도 통신 계층을 둘 필요가 없습니다.

Django도 Python 코드를 연결할 수 있지만, BINJARI의 관리 화면은 Flutter에 있고 현재 DB 접근은 `sqlite3`로 작성되어 있습니다. 이 구조에서는 Django의 기본 관리자 화면이나 ORM을 중심으로 서버를 구성할 필요가 크지 않습니다. 필요한 API를 붙여 가는 방식에는 코어를 작게 유지하는 [Flask의 설계](https://flask.palletsprojects.com/en/stable/design/)가 맞습니다. Django가 제공하는 구성은 [공식 개요](https://docs.djangoproject.com/en/5.2/intro/overview/)에서 확인할 수 있습니다.

FastAPI도 충분히 적합한 대안입니다. 다만 이 프로젝트에서 반복 계산을 줄인 방법은 프레임 스킵이며, 프레임워크를 비동기로 바꾸는 것만으로 모델 추론 자체가 빨라지지는 않습니다. [FastAPI 문서도 영상 처리와 머신러닝을 계산 중심 작업으로 구분](https://fastapi.tiangolo.com/async/#concurrency-parallelism-web-machine-learning)합니다. Flask를 쓰더라도 추론 작업의 분리, API 입력 검증, 운영 서버 구성은 별도로 관리해야 합니다. [서버 구현](app_v1.py)

</details>

<summary><strong>YOLOv8x — 학습된 빈자리와 점유 영역을 상태 판정에 활용하기</strong></summary>

전체 영상에 차량이 있는지만 분류해서는 어느 주차면이 비었는지 알 수 없습니다. BINJARI는 탐지 위치, 클래스, 신뢰도가 필요합니다. 현재 YOLOv8x 모델은 `space-empty`와 `space-occupied`를 구분하고 이 정보를 반환하므로, 각 탐지 영역을 미리 등록한 주차면에 연결할 수 있습니다. Ultralytics는 [Python에서 학습 가중치를 불러와 추론하는 인터페이스](https://docs.ultralytics.com/models/yolov8)를 제공하며 현재 서버도 이를 사용합니다.

YOLOv5도 같은 목적에 사용할 수 있고, 프로젝트에는 YOLOv5x 기반 가중치도 남아 있습니다. 현재 시연에서는 기존 코드와 운영 로그에서 사용이 확인된 YOLOv8x를 사용해 동작을 재현했습니다. 두 체크포인트의 학습 조건이 같지 않아 검증 점수만으로 모델 간 우열을 결론내리지는 않았습니다. [보관된 모델과 검증 조건](docs/MODEL.md#사용한-모델)

특히 **x 모델이 반드시 필요한지는 추가 검증이 필요합니다.** [공식 모델 표](https://docs.ultralytics.com/models/yolov8#performance-metrics)에서 x는 n/s보다 큰 모델이며 계산량도 많습니다. 같은 주차장 정답 데이터로 최종 상태 판정 오류와 처리 시간을 비교한 뒤, 작은 모델로 충분하다면 바꾸는 것이 운영 비용에 유리할 수 있습니다.

## 제가 맡은 역할

저는 **Flask 백엔드 개발, 영상 추론 주기 조정, 주차 상태 판정, SQLite 데이터 저장과 통계 처리**를 담당했습니다. 안서현이 학습한 모델의 탐지 결과를 주차면별 상태로 바꾸고, 앱에서 조회할 수 있는 API로 제공했습니다.

| 구현 | 접근 방식 | 코드 |
| --- | --- | --- |
| 영상 처리와 상태 API | 주차장별 영상 프레임을 처리하고 추론 결과를 주차면 상태로 변환 | [`ParkingSystem`](app_v1.py#L490-L715), [`_detect_vehicles`](app_v1.py#L854-L1083) |

### 탐지 결과를 실제 주차면 상태로 바꾸는 과정

모델이 찾은 박스 하나가 곧 주차면 하나를 뜻하지는 않습니다. 박스가 옆 주차면까지 걸치거나, 하나의 주차면에 여러 탐지 결과가 겹칠 수 있기 때문입니다. 그래서 모델의 결과를 그대로 빈자리 수로 세지 않고 다음 순서로 처리했습니다.

1. **주차면을 미리 지정합니다.** 카메라 영상 위에 각 주차면의 경계를 다각형 좌표로 등록합니다.
2. **탐지 결과와 주차면을 연결합니다.** 주차면 면적 중 탐지 박스가 차지하는 비율을 구하고, 이 비율에 모델의 탐지 신뢰도를 곱해 연결 점수로 사용합니다.
3. **최근 판정도 함께 확인합니다.** 순간적인 가림 때문에 한 번 탐지를 놓쳐도 상태가 바로 바뀌지 않도록 이전 결과를 반영합니다.
4. **확인 기준을 넘으면 상태를 바꿉니다.** 점유와 빈자리 전환에 서로 다른 횟수를 요구하고, 확정된 상태를 저장해 앱에 전달합니다.

여기서 사용하는 겹침 비율은 **교차 면적 ÷ 해당 주차면 면적**입니다. 두 영역의 합집합을 분모로 쓰는 IoU와는 다릅니다. [겹침 계산 코드](app_v1.py#L1132-L1155)

## 개발 중 해결한 문제

### 1. 영상의 모든 프레임을 분석하느라 정보 반영이 늦었습니다

**어려웠던 점:** 빈자리를 정확히 찾더라도 결과가 늦게 도착하면 그사이에 주차장 상황이 바뀔 수 있습니다. 운전자는 이전 정보를 보고 빈자리를 찾게 됩니다. 모델을 계속 실행하면서도 불필요한 반복 계산은 줄여야 했습니다.

**원인:** 연속된 영상 프레임은 대부분 비슷한 주차 상태를 담고 있습니다. 모든 프레임에 모델을 실행하다 보니 상태가 그대로인 장면에도 같은 계산을 반복했습니다. 차량이 주차하거나 빠져나가는 데에는 시간이 걸리므로 모든 프레임을 분석할 필요는 없다고 판단했습니다.

**해결:** 프레임 카운터를 두고 **5프레임당 1회**만 추론하도록 변경했습니다. 추론하지 않는 프레임은 모델 실행을 건너뛰고, 상태 판정은 추론이 실행된 프레임에서만 갱신합니다. [프레임 스킵 코드](app_v1.py#L695-L704)

| 항목 | 모든 프레임을 추론할 경우 | 현재 설정 |
| --- | --- | --- |
| 추론 주기 | 매 프레임 | 5프레임당 1회 |
| 추론 대상 프레임 수 | 100% | 약 20% |

**확인한 결과:** 같은 길이의 입력 영상에서 추론 대상 프레임 수를 약 **80% 줄이는 설정**입니다. 이번 시연에서도 같은 간격으로 모델을 실행했으며, 원본 프레임 번호와 실제 추론 결과를 [실행 기록](docs/MODEL.md)에 남겼습니다. 영상 읽기와 전처리까지 포함한 전체 연산량이 80% 줄었다는 뜻은 아닙니다.

**남은 문제:** 프레임을 건너뛰면 짧은 변화를 놓칠 수 있고, 서버가 상태를 판정해도 앱의 다음 조회까지 기다려야 합니다. 현재 앱은 10초 간격으로 조회하므로 추론 횟수 감소와 화면 반영 속도를 같은 성과로 설명하지 않았습니다.

### 2. 차량을 잠깐 놓쳐도 빈자리로 안내할 수 있었습니다

**문제와 원인:** 차량이 가려지거나 탐지 신뢰도가 일시적으로 낮아질 때 단일 프레임 결과로 상태를 바꾸면, 주차된 면을 빈자리로 잘못 안내할 수 있습니다.

**판단 기준:** 빈 공간을 점유로 잘못 표시하면 사용 가능한 자리를 하나 덜 안내합니다. 반대로 주차된 공간을 빈자리로 표시하면 운전자가 그 자리까지 이동했다가 다시 찾아야 합니다. 후자의 오류를 더 조심하도록 빈자리로 바꾸는 조건을 높였습니다.

**해결:** 일반 주차면은 최근 **10개 판정**을 보관하고 최근 결과와 신뢰도가 높은 결과에 더 큰 비중을 줍니다. 시간 감쇠 가중치는 `0.9`, 점유로 구분하는 가중평균 기준은 `0.7`입니다. 필터를 거친 뒤에는 현재 상태와 확인 횟수를 보관하는 상태 머신에서 전환 여부를 결정합니다.

| 전환 방향 | 일반 주차면의 확인 기준 | 의도 |
| --- | --- | --- |
| 빈자리 → 점유 | 신뢰도 기준을 충족한 점유 판정 5회 | 새로 주차한 차량을 반영 |
| 점유 → 빈자리 | 신뢰도 기준을 충족한 빈자리 판정 8회 | 일시적인 탐지 누락으로 빈자리를 안내하지 않도록 추가 확인 |

상태 머신의 신뢰도 기준은 `0.7`입니다. 기준을 충족한 반대 판정이 나오면 기존 방향의 카운터를 초기화하고, 신뢰도가 부족하면 카운터를 그대로 둡니다. 이 횟수는 원본 영상 전체가 아닌 **추론 결과를 필터링한 판정 기준**입니다. [시간 필터, 상태 머신](app_v1.py#L1225-L1405)

**예외와 한계:** 카메라 가장자리에 걸리는 55호관 B1은 별도 필터와 더 엄격한 빈자리 확인 조건을 적용했습니다. 빈자리를 잘못 안내하는 오류를 줄이는 대신, 실제 출차 직후의 반영은 늦어질 수 있습니다. 모든 주차면에 같은 설정이 맞지는 않았습니다. [B1 예외 처리](app_v1.py#L990-L1060)

**확인한 범위:** 공개한 B5 입차 영상에서는 상태가 빈자리에서 점유로 바뀌고 앱의 빈자리 수도 줄어드는 것을 확인했습니다. 이 시연만으로 오탐률이 얼마나 줄었는지까지 검증한 것은 아닙니다.

### 기록이 없는 시간대의 추천을 실제 관측값과 구분했습니다

원본 통계 코드는 저장된 점유율을 사용하되, 데이터가 부족한 시간대는 기본 혼잡 패턴과 임의 변동값으로 채웠습니다. 화면에 수치가 보여도 모두 실제로 관측한 값은 아니었습니다.

현재 코드는 점유율을 **5분 간격**으로 SQLite에 저장하고 24개 시간 구간으로 집계합니다. 현재 시간은 분석 중인 주차 상태를, 나머지 시간은 **당일 평균 → 최근 7일 평균** 순으로 사용합니다. 향후 12시간 중 기록이 있는 시간대에서 점유율이 가장 낮은 시간을 추천합니다. 기록이 없으면 `has_data=false`로 표시하고 추천에서 제외합니다.

이 기능은 기록된 혼잡도를 비교하는 안내입니다. 미래의 혼잡도를 예측하는 별도 AI 모델은 사용하지 않습니다. [점유율 기록](app_v1.py#L1074-L1082), [집계와 추천](app_v1.py#L1602-L1689)

### 주차장이 달라도 같은 주차면 ID를 쓰는 문제를 수정했습니다

**문제와 원인:** 55호관과 도서관 모두 `A1`, `B1` 같은 주차면 ID를 사용합니다. 초기 스키마처럼 ID만 기본키로 사용하면 서로 다른 주차장의 상태를 구분할 수 없습니다.

**해결:** 현재 상태 테이블의 기본키를 **`(parking_lot, id)`**로 바꿨습니다. 주차장과 주차면 ID를 함께 써서 구분하고, 상태 조회와 입출차 이력 갱신에도 두 값을 사용합니다. 기존 스키마로 생성된 상태 캐시는 초기화 시 새 스키마로 재생성합니다. [DB 스키마](app_v1.py#L335-L374), [상태와 이력 갱신](app_v1.py#L1172-L1217)

### 모델 판정과 앱 표시를 함께 확인할 수 있게 했습니다

보관된 학습 모델과 원본 영상으로 B5 입차 구간을 다시 분석하고, 프레임별 결과를 JSON으로 남겼습니다. 같은 결과를 시간 순서대로 API에 제공해 기존 Flutter 상세 화면에서도 상태가 바뀌는지 확인했습니다.

[재생 서버 테스트](tests/test_inference_replay.py)는 입차 전후의 빈자리 수와 점유율, 재생 종료 후 상태 유지, 재시작, 응답 헤더를 확인합니다. 이 테스트는 기록을 앱에 전달하는 동작을 검사하며, 모델 정확도나 실제 카메라 연결 성능을 검사하지는 않습니다.

## 한계와 개선 방향

### 카메라 위치가 바뀌면 주차면 좌표도 다시 맞춰야 합니다

현재는 영상 위에 등록한 다각형으로 주차면을 구분합니다. 카메라를 옮기거나 촬영 각도가 달라지면 같은 좌표를 그대로 쓰기 어렵습니다. 다른 주차장에 적용할 때는 모델 실행뿐 아니라 좌표 등록과 현장 확인도 필요합니다. 좌표를 설정한 뒤 기준 화면과 비교하는 기능이 있으면 설치 오류를 줄일 수 있습니다.

### 어두운 환경과 차량 가림에 대한 검증이 더 필요합니다

팀은 주간과 야간에 영상을 수집했지만, 현재 공개한 추론 시연은 주간 영상 두 개입니다. 비가 오거나 조명이 부족한 상황까지 같은 성능을 낸다고 단정할 수는 없습니다. 조건별 정답 데이터를 마련하고, 실제 점유면을 빈자리로 안내한 비율과 상태 전환 지연을 따로 측정해야 합니다.

### 판정을 신중하게 할수록 화면 반영은 늦어질 수 있습니다

시간 필터와 상태 전환 횟수는 순간적인 탐지 오류를 걸러내지만, 실제 입출차도 여러 번 확인한 뒤 반영합니다. 앱의 10초 조회 간격도 추가 대기 시간을 만듭니다. 모델 실행 시간, 서버에서 상태를 확정한 시각, 앱에 표시한 시각을 따로 기록한 뒤 조회 간격 조정이나 서버의 변경 알림 방식을 검토할 수 있습니다.

### 모델의 검증 점수가 서비스 정확도를 뜻하지는 않습니다

보관된 YOLOv8x의 학습 당시 `mAP@50`은 **97.42%**입니다. 하지만 이 값은 물체 탐지 평가 지표이며, 주차면별 최종 상태를 97.42% 맞혔다는 뜻은 아닙니다. 공간 연결과 시간 필터까지 포함한 최종 판정은 별도 정답 데이터로 평가해야 합니다. [모델 지표와 평가 조건](docs/MODEL.md#사용한-모델)

### 기록이 쌓이기 전에는 추천할 시간이 부족합니다

현재 추천은 해당 시간대의 관측 기록이 있어야 합니다. 아직 기록이 없는 시간대는 추천하지 않으며, 날씨나 학사 일정에 따른 수요 변화도 별도로 반영하지 않습니다. 충분한 기간의 기록을 모으고 요일별 차이부터 비교하는 것이 다음 개선 순서입니다.

## 배운 점

### 모델이 찾은 결과를 사용자에게 보여주기까지 별도 판단이 필요했습니다

탐지 박스를 그리는 것과 운전자에게 빈자리를 안내하는 것은 달랐습니다. 어느 주차면에 해당하는 결과인지 연결하고, 잠깐 탐지를 놓친 것인지 실제 출차인지 구분해야 했습니다. 모델 밖의 공간 계산과 상태 관리도 서비스의 안내 품질을 결정한다는 점을 배웠습니다.

### 두 종류의 오류를 똑같이 다루지 않았습니다

빈자리를 하나 덜 보여주는 오류와, 차량이 있는 곳을 빈자리로 안내하는 오류는 사용자에게 미치는 영향이 다릅니다. 이 차이를 점유 5회와 빈자리 8회라는 확인 조건에 반영했습니다. 판단 기준을 정할 때는 정확도 수치뿐 아니라 잘못된 안내를 받은 사용자가 어떤 일을 겪는지도 고려해야 했습니다.

### 개선 효과는 실제로 확인한 범위만 설명해야 합니다

추론 대상 프레임이 줄었다고 앱이 같은 비율로 빨라지는 것은 아닙니다. 모델의 검증 점수와 주차면 상태의 정확도도 다릅니다. 이번에 시연과 API 조회 기록을 함께 남기면서, 설정값으로 확인할 수 있는 변화와 직접 시간을 재거나 정답과 비교해야 하는 결과를 구분했습니다.

## 구현 결과

- 2개 주차장, **56개 주차면**을 대상으로 상태 조회 구조 구현
- 5프레임당 1회 추론으로 **추론 대상 프레임 수 약 80% 감소**
- 학습된 YOLOv8x로 두 주차장 원본 영상을 재실행하고, 탐지 결과와 주차면 상태를 나란히 보여주는 시연과 프레임별 결과 공개
- 시간 가중 필터를 적용하고 점유와 빈자리 전환의 확인 횟수를 다르게 설정해, 순간적인 탐지 누락이 곧바로 빈자리 안내에 반영되지 않도록 설계
- SQLite 기록을 활용한 시간대별 점유율 조회와 방문 시간 추천 구현
- 교내 소프트웨어 전시회 **인기상** 수상

## 실행 방법

### 분석 서버

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

export MODEL_PATH="$PWD/models/best_seo.pt"
export ADMIN_TOKEN="change-me"
python app_v1.py --no-video
```

기본 포트는 `5000`입니다. 실제 시연에 사용한 가중치는 `best_seo.pt`이며 파일 식별 정보와 환경은 [모델, 추론 재현 문서](docs/MODEL.md)에 정리했습니다. 원본 가중치는 Git 저장소에 포함하지 않으므로 `models/best_seo.pt`에 두거나 `MODEL_PATH`로 지정합니다. 도서관 입력 영상은 [`videos/library2.mp4`](videos/library2.mp4)에 있으며, 다른 영상 경로는 `VIDEO_PATH_A`, `VIDEO_PATH_B`로 지정할 수 있습니다.

### Flutter 앱

```bash
flutter pub get
flutter run --dart-define=API_BASE_URL=http://<서버 IP>:5000
```

Google Maps API 키는 Android에서 `android/local.properties`의 `MAPS_API_KEY`, iOS에서 `ios/Flutter/Secrets.xcconfig`의 `MAPS_API_KEY`로 설정합니다. 실제 기기에서 서버에 연결할 때는 `localhost` 대신 서버의 LAN IP를 사용합니다.
